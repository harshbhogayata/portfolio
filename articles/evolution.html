A portfolio is an argument about who you are. I have made that argument three times in a year, and each version says as much about how I wanted to be understood as about the work inside it.

The first was a costume, the second a clever frame, and the third, this site, is an attempt to let the work speak with its context attached. None of the earlier ones was wrong. Each was the honest answer at the time, and each taught me what the next one had to do.

The terminal

harshbhogayata.github.io10commits, 20 to 28 November 2025.

In November 2025 I was a cybersecurity analyst, and the first site made sure you knew it. It was static HTML on GitHub Pages, styled with Tailwind from a CDN and a little vanilla JavaScript. The page was almost black, the accents were a neon green, and it came with every effect the genre expects: Matrix rain, glitching text, a hidden terminal on Ctrl+K and a Konami code that switched on god mode.

Underneath the effects there was real work. Twelve small security tools ran in the browser: a hash generator, a password checker, a subnet calculator, encoders, a chmod helper, a regex tester, a port reference, a log analyser and a steganography tool, alongside blog posts on getting started in security and the OWASP top ten.

What it got right was that it did things. What it got wrong was that it looked like what a security portfolio is supposed to look like. The costume arrived before the person did.

The changelog

A “changelog-as-portfolio metaphor”, with “semantic versioning as visual backbone”.

By March 2026 I had moved towards building full products, and the second site told that story as a software release. It was a Next.js app on Vercel, set on warm paper with a serif display face and an orange accent, and it introduced itself as version 2.3.1. The first screen was a package manifest. The history was a changelog, from v0.1.0, the initial commit, through v1.0.0, security origins, and v2.0.0, the move to full stack, to v2.3.1, the first production deployment.

Projects were listed as features. Weak spots became known issues, rewritten as patches in progress. The contact form was the installation guide. It was built in an afternoon, in seven commits.

The metaphor was the best idea on the page, and that was the trouble. It did most of the talking. The projects still appeared as outcomes, a name, a line and a link, and nothing about the decisions behind them.

Two that never shipped

Between the versions there were drafts that stayed drafts. In February a newspaper-styled site, with mastheads, a note from the editor and editor’s picks, got as far as a working page. In October a Next.js site imagined as a set of technical drawings, every page a numbered sheet, ran in parallel with this one and lost. Both were good ideas wearing the same mistake as the changelog: a metaphor standing in front of the work.

Every earlier version had a metaphor standing in front of the work.

Work, with context

On recordRejected directions are written down with the reason, so nobody retries them: “too bare”, “generic”, “played safe”.

This version began in September 2026, and it is deliberately plain underneath: static HTML, assembled from a handful of fragments by a short Python script, with no framework at all. Two lines guide it. Dyson inside, Apple outside: deep engineering, a quiet surface. And aim higher, never barer: when something is not working, make the idea stronger rather than taking things away.

Instead of a metaphor it has a visual language: lines. The mark in the opening is drawn as a route from design to build to ship. In the tech stack, picking a tool draws a wire into the line from idea to production and names the projects it shipped in. Experience is a single sentence that rewrites itself as you move along a time rule. And these case studies are read along a wire that turns its corner into the next one.

The process changed as much as the look. Every redesign is built first as a separate concept copy, judged at the real size of a laptop screen, 1,280 by 632 pixels, and merged into the live site one piece at a time, only once it is approved. Directions that failed stay on record with the reason, so the same mistake is not made twice.

What changed

Looking back, the three versions move from costume, to metaphor, to evidence. The first said what I wanted to be. The second said how I had changed. This one tries to show how I work: the decisions, the constraints, what broke and what changed after release. Even the tech stack is evidence now; pick a tool and it shows you where it was used.
